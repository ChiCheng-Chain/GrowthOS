## 状态设计(DomainStatsViewModel)

```kotlin
data class DomainStatsUiState(
    val recentSamples: List<SampleWithErrorType> = emptyList(),  // F1 最近样本
    val errorDistribution: List<ErrorTypeCount> = emptyList(),    // F2 错误分布
    val inProgressTrainings: List<TrainingWithTypeName> = emptyList(), // F3 训练项
    val recentPrinciples: List<Principle> = emptyList(),          // F4 近期原则
    val filteredSamples: List<SampleWithErrorType> = emptyList(), // F5 筛选后样本
    val filter: SampleFilter = SampleFilter(),                    // 筛选条件
    val availableErrorTypes: List<ErrorTypeCount> = emptyList()   // 筛选条选项(该领域出现过的错误类型)
)

data class SampleFilter(
    val errorTypeId: Long? = null,   // null = 全部
    val attribution: Attribution? = null  // null = 全部
)

/** 训练项 + 关联错误类型名(F3 展示用)。 */
data class TrainingWithTypeName(
    val training: Training,
    val errorTypeName: String
)
```

- `selectedDomainId`:从 [SelectedDomainStore.flow](../android/app/src/main/java/com/growthos/app/data/local/SelectedDomainStore.kt) 取(与阶段 1 DomainViewModel 同源)。为避免两 ViewModel 各读一遍 store 产生不一致,DomainStatsViewModel 也注入 SelectedDomainStore(见 D1)。
- 四区块 Flow:`combine` selectedDomainId 与各 Repository 的 observe 流。selectedDomainId 为 null(无可见领域)时不查(返回空)。
- F2 错误分布用全时段(`startMillis=0, endMillis=Long.MAX_VALUE`),limit=8。
- F3 训练项:`observeByDomain(domainId)` 过滤 `status == IN_PROGRESS`;关联错误类型名用 `ErrorTypeRepository.getById` 批量解析(或 SQL JOIN——见 D3)。
- F5 筛选:`filter` 是 MutableStateFlow。筛选用 UI 层过滤 `observeWithNames(domainId)` 的结果(见 D2),或按筛选条件切 DAO 方法。
- `availableErrorTypes`:F2 的 `errorDistribution`(该领域出现过的错误类型 + 频次)直接复用做筛选条选项,不另查。

## 数据流

```
SelectedDomainStore.flow (selectedDomainId)
  → DomainStatsViewModel.combine(
      recentSamples = observeRecentByDomain(id, 5),
      errorDistribution = observeTopErrorTypes(id, 0, MAX, 8),
      trainings = observeByDomain(id) filter IN_PROGRESS + 解析错误类型名,
      principles = observeByDomain(id) take 5,
      baseSamples = observeWithNames(id),   // F5 全量该领域样本(带名)
      filter                                  // MutableStateFlow
    )
  → filteredSamples = baseSamples 按 filter 过滤
  → DomainScreen collect → 四区块 + 筛选列表渲染

切换领域:SelectedDomainStore 变 → combine 重算 → 四区块整体刷新
点错误分布条:setFilter(errorTypeId = ...) → filter 变 → filteredSamples 重算 + 滚动到样本列表
```

## 关键决策

### D1 两个 ViewModel 并列,不合并

阶段 1 的 [DomainViewModel](../android/app/src/main/java/com/growthos/app/ui/domain/DomainViewModel.kt) 管领域 chips / 选中 / 隐藏 / 对话框;阶段 3 新增 DomainStatsViewModel 管四区块统计 + 筛选。两者都依赖 selectedDomainId,各自注入 SelectedDomainStore(同源,DataStore 进程级唯一,读一致)。理由:职责分离,阶段 1 已测的逻辑不动,阶段 3 新逻辑独立测。代价:DomainScreen 取两个 ViewModel。可接受——它们状态不交叉。

### D2 筛选用 UI 层过滤,不切 DAO

F5 筛选用 `observeWithNames(domainId)` 取该领域全量样本(带错误类型名),在 ViewModel 里按 `filter` 过滤。理由:该领域样本量自用场景不大(几十到几百),内存过滤够快;切 DAO 方法(`observeByErrorType` + `observeByAttribution` 叠加)要组合查询且不带错误类型名(还要再 JOIN),复杂度高于收益。`observeWithNames` 一次 JOIN 取全,UI 过滤最简。可演进:样本量过千再下沉到 SQL。

### D3 训练项错误类型名解析用 SQL JOIN,不用逐条 getById

F3 要展示训练项关联的错误类型名。方案:TrainingDao 加 `observeInProgressByDomainWithTypeName(domainId)` JOIN error_types 一次取全(类似 SampleDao.observeWithNames)。理由:逐条 `ErrorTypeRepository.getById` 是 N+1;UI 层过滤 `observeByDomain` 再解析也绕。加一个 JOIN 查询最干净,对齐阶段 0 的 `observeWithNames` 模式。这算阶段 3 唯一的数据层增量(一个 DAO 方法 + relation POJO)。

### D4 四区块全时段统计,不做时间选择

本阶段 F2 错误分布用全时段(该领域所有样本)。时间范围选择器留阶段 4(周复盘)。理由:领域页是"看这个领域整体",周复盘页才是"看近期趋势";分开放避免领域页过载。

### D5 点错误分布条触发筛选并滚动

F2 分布条点击 → `filter.errorTypeId = 该错误类型` → F5 列表重算 + 滚动到 F5 区。这是把"统计"和"明细"连起来的关键交互(闭环第 5 步到第 7 步的衔接)。用 `LazyListState` / `rememberScrollState` 的 `animateScrollTo` 实现。归因 chips 同理可点(但归因在 F5 筛选条里已有,不必从别处触发)。

### D6 清 DomainScreen 的 SampleStub 引用,文件留阶段 4 删

阶段 2 清了 RecordScreen 对 `SampleStub.examples` 的引用,阶段 3 清 DomainScreen 对 `SampleStub.errorDistribution` 的引用。但 [WeeklyScreen](../android/app/src/main/java/com/growthos/app/ui/weekly/WeeklyScreen.kt) 仍用 `SampleStub.weeklySampleCount` / `controllableRatio` / `topErrors` / `highestEmotionSample`,故 **SampleStub 文件本阶段不删**,留阶段 4 清完 WeeklyScreen 再删。本阶段只去掉 DomainScreen 的引用,确保领域页不再依赖占位。
