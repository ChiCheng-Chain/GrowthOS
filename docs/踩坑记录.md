# GrowthOS 踩坑记录

## 文档定位

记录 GrowthOS 开发过程中踩过的、非显而易见的坑,供后续阶段与重启会话时避坑。只收"实际踩到、花时间排查、且结论非显然"的;常规 API 用法、文档可查的不收。条目按"现象 → 根因 → 对策"写。

---

## 构建 / 环境

### P1 系统默认 JDK 是 8,工程要 17+

- **现象**:`gradle test` 直接报 JDK 版本不兼容,或 KSP/AGP 起不来。
- **根因**:[build.gradle](../android/app/build.gradle#L37-L39) 配 `VERSION_17`,本机 `JAVA_HOME` 指向 `C:\Program Files\Java\jdk1.8.0_181`。
- **对策**:跑 gradle 前 `JAVA_HOME="C:/Program Files/Android/Android Studio/jbr"`(JBR 21)。Bash 工具里用 in-line 前缀设,不持久,每次 gradle 调用都要带。

### P2 工程缺 gradlew 脚本

- **现象**:`./gradlew` 找不到;`gradle wrapper` 生成脚本时校验 `services.gradle.org` 失败(本机走阿里云镜像,直连官方源不通)。
- **根因**:`android/gradle/wrapper/` 下只有 `gradle-wrapper.properties`,没有 `gradlew` / `gradlew.bat`。`gradle wrapper` task 默认校验官方 distribution URL,网络不通就挂。
- **对策**:直接用缓存里已下载的 gradle 二进制:
  ```
  cd /d/GrowthOS/android && JAVA_HOME="C:/Program Files/Android/Android Studio/jbr" \
    "C:/Users/mlamp/.gradle/wrapper/dists/gradle-8.10.2-bin/9x0at1uld387do03q0roict4h/gradle-8.10.2/bin/gradle" \
    :app:testDebugUnitTest --console=plain
  ```

### P3 Bash 工具工作目录在会话切换后会丢失

- **现象**:`gradle` 报 `Directory 'D:\GrowthOS' does not contain a Gradle build`,但上次明明在 `android/` 下跑过。
- **根因**:Bash 工具说工作目录持久,但会话切换(上下文重开)后 cwd 退回主工作目录 `d:\GrowthOS`(无 settings.gradle,settings 在 `android/` 子目录)。
- **对策**:每次 gradle 调用都带 `cd /d/GrowthOS/android &&` 前缀,别依赖上次的 cwd。

### P4 后台 gradle 任务被会话切换打断,留下孤儿进程锁文件

- **现象**:`testDebugUnitTest` 报 `Unable to delete directory '.../build/test-results/testDebugUnitTest/binary' ... output.bin`,连 `cleanTestDebugUnitTest` 也删不掉;或 `bundleDebugClassesToRuntimeJar` 报 `classes.jar: 另一个程序正在使用此文件`,即便没会话切换也会撞(多个 gradle 调用并发或上一次没退干净)。
- **根因**:后台跑的 gradle 任务被停/并发时,`Gradle Test Executor` worker 进程(命令行含 `Gradle Test Executor N`)或编译 worker 没退,锁着 `output.bin` / `classes.jar`。
- **对策**:PowerShell `Get-Process java` 找命令行含 `Gradle Test Executor` 的 java PID,`Stop-Process -Id <pid> -Force` 杀掉,再 `rm -rf` 对应被锁的 `binary` / `runtime_app_classes_jar` 目录,重跑。杀进程时只杀 test executor + 对应 gradle launcher,留 daemon 和 kotlin daemon 无害。锁的可能是 test binary 也可能是 runtime jar,认准命令行里的 `Gradle Test Executor` 标识即可。

### P4.5 Bash 工具偶发对 JBR java 报 Permission denied,改用 PowerShell 跑 gradle

- **现象**:Bash 工具里带 `JAVA_HOME="C:/Program Files/Android/Android Studio/jbr"` 前缀跑 gradle,偶发 `line 252: .../jbr/bin/java: Permission denied`(同一命令上次能跑)。PowerShell 直接 `& java -version` 却正常。
- **根因**:Bash 工具的 sandbox 对 `Program Files` 下可执行文件的访问授权偶发失效,非路径或 JDK 问题。
- **对策**:撞到就改用 PowerShell 工具跑——`$env:JAVA_HOME="C:\Program Files\Android\Android Studio\jbr"; Set-Location D:\GrowthOS\android; & "C:\Users\mlamp\.gradle\wrapper\dists\gradle-8.10.2-bin\...\gradle.bat" :app:testDebugUnitTest --console=plain`。注意 PowerShell 输出是 UTF-16 LE,`tail`/`grep` 看着字符间有空格,但内容可读;用 `Tee-Object` 落盘后 Monitor grep 仍能匹配关键词。

### P4.6 DataStore Preferences flow 走 IO 线程,ViewModel 单测用 StandardTestDispatcher 推不动

- **现象**:`DomainViewModelTest` 里 `vm.uiState.value` 在 `advanceUntilIdle` 后仍是初始空 state;部分用例报 `UncompletedCoroutinesError`。
- **根因**:`uiState` 用 `combine(repo.observeVisible(), repo.observeAll(), selectedStore.flow, dialogState)`。`SelectedDomainStoreImpl.flow` 是 DataStore 的 `data.map{...}`,读在 `Dispatchers.IO` 上跑,不归 `StandardTestDispatcher` 管,`advanceUntilIdle` 永远等不到它的第一个 emit,combine 卡住。
- **对策**:持久化类(`SelectedDomainStore`)抽成 interface,生产用 DataStore 实现,单测注入内存 `MutableStateFlow` 假实现——ViewModel 状态逻辑测试不再依赖真 IO,时序完全受测试 dispatcher 控制。真 DataStore 往返由独立的 `SelectedDomainStoreTest`(Robolectric)覆盖。`runTest(testDispatcher)` 显式传 dispatcher,确保 runTest 协程与 viewModelScope(Main 被替换成 testDispatcher)在同一 scheduler。

## Room / SQLite

### P5 SeedCallback 不能用异步协程跑 execSQL

- **现象**:in-memory DB 单测大面积挂 `SQLiteConstraintException` + `com.almworks.sqlite4java.SQLiteException`,但种子插入测试和 TypeConverter 测试过。凡 insert 带 FK 的 Sample/Training 全挂。
- **根因**:[GrowthOSDatabase](../android/app/src/main/java/com/growthos/app/data/local/GrowthOSDatabase.kt) 的 `SeedCallback.onCreate` 原用 `CoroutineScope(Dispatchers.IO).launch { db.execSQL(...) }` 异步插种子。`SupportSQLiteDatabase` 非线程安全,`onCreate` 传入的 `db` 仅在该回调线程有效;另起协程用它会触发 sqlite4java 连接异常,污染后续 insert。
- **对策**:`onCreate` 里直接同步 `db.execSQL`,不另起协程。`onCreate` 本就在写线程执行,插 8 行很快,不阻塞。

### P6 INSERT OR IGNORE 冲突时返回 -1,会污染外键

- **现象**:测试里 `insert(ErrorType(name="边界条件遗漏"))` 后用返回的 id 插 Sample,外键约束失败。种子已含同名错误类型时尤其稳定复现。
- **根因**:[ErrorTypeDao](../android/app/src/main/java/com/growthos/app/data/local/dao/ErrorTypeDao.kt) 用 `@Insert(onConflict = OnConflictStrategy.IGNORE)`。name 唯一索引下,重名时 insert 被 IGNORE,Room 返回 **-1**。用 -1 当 errorTypeId 插 Sample,FK 约束挂掉。
- **对策**:重名是预期(R-004 跨领域复用),insert 后若返回 ≤0 就 `getByName` 取已存在行的真实 id。`ErrorTypeRepository.getOrCreate` 已封装此逻辑;测试里也用同样兜底,别假设 insert 一定返回正 id。
- **影响 UI 层**:阶段 2 录入页"新建并立即选中"错误类型时,必须走 `getOrCreate`,不能拿 insert 返回值直接用。

### P7 Robolectric 下 NULLS LAST 不可用,且"全 null 返回 null"要靠 WHERE

- **现象**:`observeHighestEmotion` 在"窗口内样本情绪强度全为 null"时应返回 null,实际返回了那条 null 样本。
- **根因**:原 SQL 用 `ORDER BY emotionIntensity IS NULL, emotionIntensity DESC` 想替代 `NULLS LAST`。但这只把 null 排到后面,行还在,LIMIT 1 照样返回它。`NULLS LAST` 在 Robolectric 的 legacy SQLite(`ShadowLegacySQLiteConnection` + sqlite4java,API 26 旧 SQLite)上语法不通。
- **对策**:语义应是"没有非空情绪样本时返回 null",用 `WHERE emotionIntensity IS NOT NULL` 过滤,而非靠排序。全 null 时查不到行,Flow emit null。排序简化为 `ORDER BY emotionIntensity DESC`。

### P8 Robolectric + Room in-memory DB 是可行路径,但要看 sdk 与引擎

- **现象**:`gradlew test` 能跑 Room in-memory DB 测试,不连真机。
- **对策**:`@RunWith(RobolectricTestRunner::class)` + `@Config(sdk = [33])`,`GrowthOSDatabase.createInMemory(context)`。引擎是 `ShadowLegacySQLiteConnection`(sqlite4java),行为偶尔与真机 SQLite 有差异(见 P7),遇到时按真机语义为准、SQL 兼容写法兜底。`app/build.gradle` 已开 `testOptions.unitTests.includeAndroidResources = true`;测试依赖走 `testImplementation`:robolectric、room-testing、androidx-test-core、kotlinx-coroutines-test。

## Compose

### P9 FlowRow 在 Compose BOM 2024.12.01 下需 @OptIn

- **现象**:一期 [DomainScreen.kt](../android/app/src/main/java/com/growthos/app/ui/domain_view/DomainScreen.kt) 编译报 `The API of this layout is experimental`。
- **根因**:`FlowRow` 在该 Compose BOM 下从稳定变实验性,需显式 opt-in。
- **对策**:用 `FlowRow` 的函数加 `@OptIn(ExperimentalLayoutApi::class)`,补 `import androidx.compose.foundation.layout.ExperimentalLayoutApi`。后续阶段用 FlowRow 同理。

### P10 Truth 断言库默认不在依赖里

- **现象**:测试写 `assertThat(...)` 编译不过,`com.google.common.truth` 找不到。
- **根因**:工程没引 truth 依赖,也没必要为一个单测引。
- **对策**:用 JUnit 原生断言(`assertEquals` / `assertNull` / `assertTrue`),不引 truth。

### P13 SharedFlow(replay=0)无订阅者时 tryEmit 丢弃,单测 events.first() 卡死

- **现象**:`SampleViewModelTest` 的 `save emits Saved event` 用例报 `UncompletedCoroutinesError at TestBuilders.kt:354`。ViewModel 用 `MutableSharedFlow<SampleEvent>(extraBufferCapacity = 1)` 发一次性事件,`save()` 里 `tryEmit(Saved)`;测试在 `advanceUntilIdle` 后调 `vm.events.first()`,协程永不完成。
- **根因**:SharedFlow 默认 `replay = 0`。`extraBufferCapacity` 只在**有订阅者排队时**起缓冲作用;无订阅者时 `tryEmit` 的值**直接丢弃**(replay=0 不缓存历史)。`save()` 的 emit 发生在无订阅者期间,之后 `first()` 开始 collect 已晚,永远等不到下一个 emit → 协程挂起不完成。
- **对策**:测试一次性事件必须**先订阅再触发**:`launch { vm.events.toList(collected) }` 起订阅,再 `save()`,`advanceUntilIdle` 后 `job.cancel()`,断言 `collected.contains(Saved)`。生产代码若依赖"事件可后取"(如配置变更后恢复),改 `replay = 1`;但导航类一次性事件用 replay=0 + 先订阅测试即可。

## 会话 / 工作流

### P11 后台命令要配 Monitor 盯关键词,别空轮询

- **现象**:`gradle test` 跑几分钟,反复 `Read` 输出文件是 wasted call(文件没变)。
- **对策**:命令用 `run_in_background: true` 跑,同时 `Monitor` tail 输出文件 + grep 关键词(`BUILD SUCCESSFUL|BUILD FAILED|FAILED|> Task :app:test|error:|tests completed`)。Monitor 在命中时通知,期间继续干别的。注意 grep 要覆盖成功和失败两种信号,别只盯成功(否则构建挂了静默不报)。

### P12 监控脚本要覆盖失败信号,不能只盯成功

- **现象**:Monitor grep 只写 `BUILD SUCCESSFUL`,构建挂了 tail 没匹配,Monitor 一直静默到超时。
- **对策**:grep alternation 必须含 `BUILD FAILED` / `FAILURE:` / `FAILED` / `error:` / `tests completed.*failed` 等失败签名。原则:沉默 ≠ 成功,覆盖不了所有终态就别上 Monitor。
