# GrowthOS 产品定位文档

## 1. 产品定义

GrowthOS 是一个面向个人成长的跨领域复盘与刻意训练系统。

它不是日记、待办、习惯打卡或普通训练记录工具。它的核心目标是帮助用户在任意领域中，把失败样本转化为可观察的错误模式，再把错误模式转化为专项训练，最终沉淀出自己的方法论。

一句话定位：

> 一个跨领域的个人复盘系统，用最低记录成本捕获失败样本，识别高频可控错误，并把它们转化为专项训练和可迁移方法论。

## 2. 问题背景

人在学习复杂领域时，常常能较快达到“强于普通人”的水平，但之后会进入瓶颈期。

瓶颈的常见原因不是基础知识完全不足，而是：

- 不清楚自己真实的失败点在哪里。
- 单次失败容易被情绪化解释。
- 没有持续记录失败样本。
- 无法识别高频、高代价的可控错误。
- 复盘不能转化成下一阶段训练。
- 不同领域的经验没有被抽象成通用方法论。

GrowthOS 要解决的是这个问题：让用户从“凭感觉努力”进入“可观察、可反馈、可训练的进步闭环”。

## 3. 核心用户

初始用户是产品创建者本人。

典型特征：

- 对多个复杂领域都有兴趣，例如编程、策略游戏、竞技游戏、运动、表达创作等。
- 学习速度较快，基础知识积累能力强。
- 已经能超过普通水平，但在稳定性、抗压、复盘、专项训练上遇到瓶颈。
- 希望通过一个领域的突破，形成可迁移到其他领域的学习方法论。

第一阶段不面向大众用户做泛化设计，优先保证个人真实使用。

## 4. 产品核心假设

用户真正需要记录的不是“今天做了什么”，而是：

1. 我经历了什么关键样本？
2. 这次失败、波动或重大问题的主因是什么？
3. 哪部分是我可控的？
4. 这个错误是否重复出现？
5. 我接下来应该训练哪个点？
6. 训练后这个错误是否减少？
7. 我能从中提炼出什么可迁移原则？

如果这些问题能被持续回答，用户就能建立自己的进步闭环。

## 5. MVP 范围

第一版定位为：极简个人复盘工具 + 少量方法论实验室。

MVP 只验证一个闭环：

1. 选择领域。
2. 记录一次失败或关键样本。
3. 选择或新增错误类型。
4. 标记归因类型。
5. 每周汇总最高频错误。
6. 创建一个专项训练目标。
7. 训练一段时间后对比错误频率变化。
8. 写下一条“我学到的原则”。

第一版不做大而全的平台。核心目标是确认用户能持续使用，并且记录能真实帮助用户发现高频错误。

## 6. 核心概念

### 6.1 领域

用户想要进步的具体领域。

示例：

- 编程
- 酒馆战旗
- 羽毛球
- CF
- 拳击
- 写作
- 演讲

### 6.2 样本

一次值得记录的关键事件。

示例：

- 一局游戏
- 一场球
- 一次线上 bug
- 一次项目返工
- 一次训练
- 一次失败的表达或沟通

### 6.3 结果

样本造成的结果或外部反馈。

示例：

- 胜负
- 排名
- 分数变化
- 是否达标
- 是否返工
- bug 影响范围
- 主观完成质量

### 6.4 错误类型

导致失败、波动或重大问题的主要可描述原因。

示例：

- 边界条件遗漏
- 信息不足就行动
- 对局面判断错误
- 贪收益导致下限崩盘
- 执行变形
- 压力下急躁
- 复查不足
- 转型太晚
- 忽略反馈信号

错误类型允许用户自由新增，但产品应鼓励复用已有类型，以便后续统计。

### 6.5 归因类型

对本次样本主因的归类。

初始枚举：

- 可控错误
- 不可控波动
- 对手或外部强
- 环境问题

归因的作用是减少情绪化，把失败拆成可训练部分和不可控部分。

### 6.6 训练项

针对一个高频或高代价错误建立的阶段性训练目标。

示例：

- 未来两周，所有涉及状态流的代码修改都先列状态表，再写代码。
- 酒馆战旗连续 30 局重点记录是否因贪升本导致掉血失控。
- 羽毛球训练两周被压反手后的过渡质量。

### 6.7 原则

从多个样本或训练周期中沉淀出的可迁移认知。

示例：

- 在高随机性系统中，不能只看单次结果，要看自己是否扩大了坏运气的惩罚。
- 复杂状态修改前，先列完整状态空间，比事后补 bug 成本更低。
- 压力下做不到的动作，不算真正掌握。

## 7. 样本记录字段

第一版记录一次样本时，只保留必要字段：

- 领域
- 时间
- 结果
- 一句话描述
- 主要错误类型
- 归因类型
- 情绪强度，可选
- 一句话复盘：下次怎么做

编程领域示例：

- 领域：编程 / 订单系统
- 时间：2026-07-20 15:00
- 结果：线上 bug，影响部分退款订单，返工 2 小时
- 一句话描述：修改订单状态逻辑时，没有处理退款中状态，导致部分订单被错误标记为已完成
- 主要错误类型：边界条件遗漏
- 归因类型：可控错误
- 情绪强度：4/5
- 一句话复盘：涉及状态流修改时，先列出所有状态和合法迁移，再补至少一个异常状态回归测试

## 8. 核心页面

### 8.1 今日记录页

打开产品后优先进入记录，而不是复杂仪表盘。

目标是降低摩擦，让用户能在 30 秒到 2 分钟内完成一次关键样本记录。

### 8.2 领域页

展示某个领域的复盘视图。

包含：

- 最近样本
- 错误类型分布
- 高频错误
- 当前训练项
- 近期原则

### 8.3 周复盘页

自动汇总最近 7 天或最近 N 条记录。

包含：

- 本周记录数
- 高频错误前三
- 可控错误占比
- 最容易引发情绪波动的错误
- 当前最值得训练的瓶颈
- 本周沉淀的一条原则

### 8.4 原则库

沉淀用户自己的跨领域方法论。

原则可以关联到领域、错误类型、训练项和样本，但第一版不需要做复杂知识图谱。

## 9. 第一版不做的事情

MVP 暂不包含：

- 社区分享
- 多人协作
- AI 自动分析
- 视频或截图上传
- 复杂统计图
- 领域专业模板库
- 复杂提醒系统
- 积分、等级、成就系统
- 账号体系
- 云同步

这些功能可能有价值，但会干扰第一阶段最重要的验证：用户是否能持续记录，并从记录中发现高频错误。

## 10. 成功标准

MVP 是否成功，不以功能数量判断，而以使用闭环是否成立判断。

第一阶段成功标准：

1. 用户能连续使用 2 到 4 周。
2. 每次样本记录能在 30 秒到 2 分钟内完成。
3. 累积 20 条样本后，用户能看出高频错误。
4. 高频错误能自然转化成一个专项训练项。
5. 训练 1 到 2 周后，同类错误频率出现下降或被更清晰地解释。
6. 用户能沉淀出至少 3 条跨领域原则。

如果以上标准成立，说明产品的核心价值成立，可以进入下一阶段迭代。

## 11. 技术定位建议

第一版建议做成本地优先的网页应用或渐进式网页应用。

建议原则：

- 优先本地可用。
- 第一版不要求登录。
- 第一版不要求云同步。
- 数据结构清晰，便于后续迁移。
- 支持 JSON 或 Markdown 导出。
- 优先使用熟悉技术栈，降低实现成本。

可选技术方向：

- 前端：React、Next.js、Vue 均可。
- 存储：IndexedDB、本地 SQLite 或轻量后端 SQLite。
- 部署：本地运行、个人服务器或静态部署均可。

## 12. 后续迭代方向

在 MVP 使用验证成立后，再考虑：

- 领域模板库
- 训练项周期管理
- 趋势图和统计分析
- AI 辅助复盘
- 自动生成周报
- 多设备同步
- Markdown 导出成长报告
- 公开分享个人方法论

后续功能必须服务于核心闭环，避免产品变成泛记录工具。

## 13. 产品原则

GrowthOS 的产品原则：

- 记录低摩擦。
- 复盘强约束。
- 归因去情绪化。
- 训练可验证。
- 方法论可沉淀。
- 先服务个人真实突破，再考虑对外分享。

最终目标不是记录更多信息，而是让用户更稳定地发现并消灭高频可控错误，从而在复杂领域中形成可迁移的成长方法。
